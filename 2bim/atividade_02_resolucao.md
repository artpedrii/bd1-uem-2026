# Parte 1 — Identificação de problemas de normalização

## Exercício 1 — Identificando redundâncias

**a)** Repetem-se `id_curso`, `nome_curso` e `coordenador`. "Sistemas de Informação / Carlos" aparece 3 vezes e "Ciência da Computação / Fernanda" aparece 2 vezes.

**b)** A repetição causa desperdício de espaço, risco de **inconsistência** (uma linha atualizada e outra não) e as chamadas **anomalias** de inserção, atualização e exclusão.

**c)** Seria preciso alterar **todas** as linhas do curso (Ana, Bruno e Pedro). Se alguma fosse esquecida, o curso teria dois coordenadores diferentes.

**d)** Ao excluir o único aluno de um curso, perde-se também a informação do curso (nome e coordenador). É a **anomalia de exclusão**.

**e)** **Não.** A chave da tabela é `id_aluno`, que não pode ser nula. Cadastrar um curso exige um aluno, e isso é a **anomalia de inserção**.

**f)** Duas entidades: **CURSO** e **ALUNO**.

```text
ANTES:  ALUNO_CURSO(id_aluno PK, nome_aluno, id_curso, nome_curso, coordenador)

DEPOIS: CURSO(id_curso PK, nome_curso, coordenador)
        ALUNO(id_aluno PK, nome_aluno, id_curso FK → CURSO)
```

## Exercício 2 — Anomalias de manipulação de dados

**a) Inserção:** não é possível cadastrar o departamento "RH" sem ter um funcionário, pois `id_funcionario` é a PK e não pode ser nula.

**b) Atualização:** se o gerente do departamento TI mudar, é preciso alterar a linha de cada funcionário do TI. Esquecer uma gera inconsistência.

**c) Exclusão:** ao excluir o único funcionário de um departamento, perdem-se nome e gerente do departamento.

**d) FUNCIONARIO:** `id_funcionario`, `nome_funcionario`, `salario` (e `id_departamento` como FK).

**e) DEPARTAMENTO:** `id_departamento`, `nome_departamento`, `gerente_departamento`.

**f)**
```text
DEPARTAMENTO(id_departamento PK, nome_departamento, gerente_departamento)
FUNCIONARIO(id_funcionario PK, nome_funcionario, salario,
            id_departamento FK → DEPARTAMENTO)
```

## Exercício 3 — Identificando dependências funcionais

**a)** Chave primária: `id_produto`.

**b)**
```text
id_produto   → nome_produto, preco, id_categoria
id_categoria → nome_categoria
id_produto   → nome_categoria   (transitiva)
```

**c)** **Sim**, mas **indiretamente**: `id_produto → id_categoria → nome_categoria`.

**d)** **Não.** Uma categoria possui vários produtos, então o `id_categoria` não identifica um único `nome_produto`.

**e)** **Sim:** `id_produto → id_categoria → nome_categoria`. O atributo não-chave `nome_categoria` depende de outro atributo não-chave (`id_categoria`).

**f)** **Sim.** Está na 1FN e na 2FN (chave simples), mas **viola a 3FN** pela dependência transitiva. Isso gera redundância do `nome_categoria`.

# Parte 3 — Primeira Forma Normal (1FN)

## Exercício 5 — Aplicando a Primeira Forma Normal

**a)** A coluna `telefones` guarda vários valores em um único campo (não atômico). Como é preciso consultar, cadastrar e excluir telefones **individualmente**, isso viola a 1FN para esse domínio.

**b)** Atributo problemático: `telefones`.

**c)** Criar uma tabela própria para telefones, com uma linha por telefone.

**d)** PKs: `CLIENTE(id_cliente)` e `TELEFONE(id_telefone)`.

**e)** FK: `TELEFONE.id_cliente → CLIENTE.id_cliente`.

**f)** **1:N** (um cliente possui vários telefones; cada telefone pertence a um cliente).

**g)** Modelo lógico:
```text
CLIENTE(id_cliente PK, nome_cliente)
TELEFONE(id_telefone PK, numero, id_cliente FK → CLIENTE)
```

### Parte prática

**h)**
```sql
CREATE TABLE cliente_ex5 (

CREATE TABLE telefone_ex5 (

```

## Exercício 6 — Grupos repetitivos

**a)** As colunas `disciplina_1`, `disciplina_2` e `disciplina_3` formam um **grupo repetitivo**, o que viola a 1FN.

**b)** Há limite fixo de disciplinas, muitos `NULL`, consultas complicadas (é preciso olhar 3 colunas para achar uma disciplina), duplicação do nome da disciplina e dificuldade para alterar ou excluir uma matrícula.

**c)** Seria necessário alterar a estrutura (`ALTER TABLE ... ADD COLUMN`) e as consultas. A solução não escala.

**d)**
```text
ALUNO(id_aluno PK, nome_aluno)
DISCIPLINA(id_disciplina PK, nome_disciplina)
MATRICULA(id_aluno FK, id_disciplina FK, PK(id_aluno, id_disciplina))
```

**e)** **N:M** entre aluno e disciplina, resolvida pela tabela associativa `MATRICULA` (duas relações 1:N).

**f)**
```sql
CREATE TABLE aluno_ex6 (

CREATE TABLE disciplina_ex6 (
    id_disciplina   BIGINT PRIMARY KEY,

    PRIMARY KEY (id_aluno, id_disciplina)
);
```

# Parte 4 — Segunda Forma Normal (2FN)

## Exercício 7 — Dependência parcial

**a)** `(id_pedido, id_produto)`

**b)** `(id_pedido, id_produto) → quantidade`

**c)** `id_produto → nome_produto`

**d)** O nome do produto é determinado só por `id_produto`, sem precisar de `id_pedido`. Logo depende de **parte** da chave composta.

**e)** **Sim**, está na 1FN: os valores são atômicos e não há grupos repetitivos.

**f)** **Não**, pois há dependência parcial (`id_produto → nome_produto`) de um atributo não primo.

**g)** Separar o que depende só de `id_produto`:
```text
PRODUTO(id_produto PK, nome_produto)
ITEM_PEDIDO(id_pedido, id_produto, quantidade)
```

**h)**
```text
PEDIDO(id_pedido PK)
PRODUTO(id_produto PK, nome_produto)
ITEM_PEDIDO(id_pedido FK, id_produto FK, quantidade,
            PK(id_pedido, id_produto))
```

### Parte prática

**i–k)**
```sql
CREATE TABLE pedido_ex7 (
    id_pedido BIGINT PRIMARY KEY
);

CREATE TABLE produto_ex7 (
    id_produto   BIGINT PRIMARY KEY,
    nome_produto VARCHAR(100) NOT NULL

CREATE TABLE item_pedido_ex7 (
    id_pedido  BIGINT  NOT NULL REFERENCES pedido_ex7 (id_pedido),
    id_produto BIGINT  NOT NULL REFERENCES produto_ex7 (id_produto),
    quantidade INTEGER NOT NULL CHECK (quantidade > 0),
    PRIMARY KEY (id_pedido, id_produto)   -- PK composta
);
```

**l)**
```sql
INSERT INTO pedido_ex7 (id_pedido) VALUES (1), (2), (3);
```

**m)**
```sql
INSERT INTO produto_ex7 (id_produto, nome_produto)

```

**n)**
```sql
INSERT INTO item_pedido_ex7 (id_pedido, id_produto, quantidade)

```

**o)**
```sql

```


**p)** A **chave primária composta** `(id_pedido, id_produto)` impede repetir o mesmo produto no mesmo pedido.

# Parte 5 — Terceira Forma Normal (3FN)

## Exercício 9 — Dependência transitiva

**a)** `id_aluno`

**b)**
```text
id_aluno   → nome_aluno, id_curso
id_curso   → nome_curso, coordenador
```

**c)** `id_aluno → id_curso → nome_curso` e `id_aluno → id_curso → coordenador`.

**d)** Está na 2FN porque está na 1FN e a chave é simples, então não há dependências parciais.

**e)** Não está na 3FN porque `nome_curso` e `coordenador` (não primos) dependem de `id_curso`, que também não é chave.

**f–h)**
```text
CURSO(id_curso PK, nome_curso, coordenador)
ALUNO(id_aluno PK, nome_aluno, id_curso FK → CURSO)
```
PKs: `CURSO.id_curso` e `ALUNO.id_aluno`. FK: `ALUNO.id_curso`.

### Parte prática

**i)**
```sql
CREATE TABLE curso_ex9 (
    id_curso     BIGINT PRIMARY KEY,

    coordenador  VARCHAR(100) NOT NULL
);

CREATE TABLE aluno_ex9 (
    id_aluno   BIGINT PRIMARY KEY,
    nome_aluno VARCHAR(100) NOT NULL,
    id_curso   BIGINT NOT NULL REFERENCES curso_ex9 (id_curso)
);
```

**j)**
```sql
INSERT INTO curso_ex9 (id_curso, nome_curso, coordenador)

    (20, 'Ciência da Computação', 'Fernanda'),
    (30, 'Engenharia de Software', 'Roberto');
```

**k)**
```sql
INSERT INTO aluno_ex9 (id_aluno, nome_aluno, id_curso)
VALUES
    (1, 'Ana', 10), (2, 'Bruno', 10), (3, 'Maria', 20),

```

**a)**

### Questão para discussão

A normalização **não elimina todos os problemas de integridade**. Ela reduz redundância e anomalias, mas continuamos precisando de restrições SQL: `NOT NULL` (obrigatoriedade), `CHECK` (preço >= 0), `UNIQUE` (ex.: CPF) e `FOREIGN KEY` (impedir referências a registros inexistentes). Normalização organiza a estrutura. As restrições garantem a validade dos valores e dos relacionamentos.

## Exercício 12 — Migrando dados de uma tabela não normalizada

```sql
CREATE TABLE produto_original (
    id_produto BIGINT PRIMARY KEY,
    nome_produto VARCHAR(100) NOT NULL,
    preco NUMERIC(10,2) NOT NULL,
    id_categoria BIGINT NOT NULL,
    nome_categoria VARCHAR(100) NOT NULL
);

INSERT INTO produto_original
(id_produto, nome_produto, preco, id_categoria, nome_categoria)
VALUES
(1, 'Notebook', 3500.00, 10, 'Informática'),
(2, 'Mouse', 80.00, 10, 'Informática'),
(3, 'Teclado', 150.00, 10, 'Informática'),
(4, 'Monitor', 1200.00, 20, 'Eletrônicos'),
(5, 'Webcam', 180.00, 20, 'Eletrônicos'),
(6, 'Impressora', 900.00, 30, 'Escritório');
```

**a)** Há redundância de `id_categoria`/`nome_categoria` em vários produtos e dependência transitiva (`id_produto → id_categoria → nome_categoria`), ou seja, a tabela viola a 3FN. Também há anomalias de inserção, atualização e exclusão.

**b)**
```text
id_produto   → nome_produto, preco, id_categoria
id_categoria → nome_categoria
```

**c)**
```text
CATEGORIA_NORMALIZADA(id_categoria PK, nome_categoria)
PRODUTO_NORMALIZADO(id_produto PK, nome_produto, preco, id_categoria FK)
```

**d)**
```sql
CREATE TABLE categoria_normalizada (
    id_categoria   BIGINT PRIMARY KEY,
    nome_categoria VARCHAR(100) NOT NULL
);

CREATE TABLE produto_normalizado (
    id_produto   BIGINT PRIMARY KEY,
    nome_produto VARCHAR(100) NOT NULL,
    preco        NUMERIC(10,2) NOT NULL CHECK (preco >= 0),
    id_categoria BIGINT NOT NULL REFERENCES categoria_normalizada (id_categoria)
);
```

**e)**
```sql
INSERT INTO categoria_normalizada (id_categoria, nome_categoria)
SELECT DISTINCT id_categoria, nome_categoria
FROM produto_original;
```
`DISTINCT` remove linhas repetidas do resultado, então cada categoria é inserida uma única vez.

**f)**
```sql
INSERT INTO produto_normalizado (id_produto, nome_produto, preco, id_categoria)
SELECT id_produto, nome_produto, preco, id_categoria
FROM produto_original;
```

**g)**
```sql
SELECT * FROM categoria_normalizada;
SELECT * FROM produto_normalizado;
```

**h)** Esta consulta deve retornar **0 linhas** (nenhum produto original ficou de fora):
```sql
SELECT *
FROM produto_original
WHERE id_produto NOT IN (SELECT id_produto FROM produto_normalizado);
```
Também se pode comparar visualmente: os 6 produtos devem aparecer em `produto_normalizado`.

**i)** Os produtos referenciam as categorias pelo identificador. Se os ids fossem recriados, os vínculos originais seriam quebrados ou trocados. Preservá-los mantém a **correspondência exata** produto-categoria dos dados originais.

**j)** A FK garante que todo `id_categoria` em `produto_normalizado` exista em `categoria_normalizada`. Isso impede produtos órfãos e impede excluir uma categoria ainda em uso.

# Parte 7 — Desafio final

## Exercício 13 — Sistema de gerenciamento de pedidos

### Etapa 1 — Análise

**a)** Atributos: `id_pedido`, `id_produto`, `data_pedido`, `id_cliente`, `nome_cliente`, `telefone_cliente`, `nome_produto`, `preco_atual_produto`, `quantidade`, `preco_unitario_venda`.

**b)** PK: `(id_pedido, id_produto)`.

**c)**
```text
id_pedido  → data_pedido, id_cliente
id_cliente → nome_cliente, telefone_cliente
id_produto → nome_produto, preco_atual_produto
(id_pedido, id_produto) → quantidade, preco_unitario_venda
```

**d)** Dependências parciais:
```text
id_pedido  → data_pedido, id_cliente
id_produto → nome_produto, preco_atual_produto
```

**e)** Dependência transitiva:
```text
id_pedido → id_cliente → nome_cliente, telefone_cliente
```

**f)** Não está na 2FN porque atributos não primos (`data_pedido`, `id_cliente`, `nome_produto`, `preco_atual_produto`) dependem de apenas parte da chave composta.

**g)** `nome_cliente` e `telefone_cliente` dependem de `id_cliente` (atributo não chave), o que é uma dependência transitiva e viola a 3FN.

### Etapa 2 — Normalização

**h) 1FN:** já atende (valores atômicos, sem grupos repetitivos, com chave definida).

**i) 2FN:** remover as dependências parciais.
```text
PEDIDO(id_pedido PK, data_pedido, id_cliente, nome_cliente, telefone_cliente)
PRODUTO(id_produto PK, nome_produto, preco_atual_produto)
ITEM_PEDIDO(id_pedido, id_produto, quantidade, preco_unitario_venda)
```

**j) 3FN:** remover a dependência transitiva.
```text
CLIENTE(id_cliente PK, nome_cliente, telefone_cliente)
PEDIDO(id_pedido PK, data_pedido, id_cliente FK)
PRODUTO(id_produto PK, nome_produto, preco_atual_produto)
ITEM_PEDIDO(id_pedido FK, id_produto FK, quantidade, preco_unitario_venda,
            PK(id_pedido, id_produto))
```

**k)** O modelo final é o do item (j).

**l) PKs:** `CLIENTE.id_cliente`, `PEDIDO.id_pedido`, `PRODUTO.id_produto`, `ITEM_PEDIDO(id_pedido, id_produto)`.

**m) FKs:** `PEDIDO.id_cliente → CLIENTE`, `ITEM_PEDIDO.id_pedido → PEDIDO`, `ITEM_PEDIDO.id_produto → PRODUTO`.

**n) Cardinalidades:**
```text
CLIENTE 1 ── N PEDIDO
PEDIDO  1 ── N ITEM_PEDIDO
PRODUTO 1 ── N ITEM_PEDIDO
PEDIDO  N ── N PRODUTO   (resolvido por ITEM_PEDIDO)
```

**z)** O `preco_atual_produto` é o preço **de hoje**, enquanto o `preco_unitario_venda` é o preço **cobrado naquele momento**. Eles são fatos diferentes, e o segundo depende de `(id_pedido, id_produto)`, não só do produto. Mantê-los separados preserva o **histórico das vendas**: reajustes futuros não alteram valores de vendas passadas, o que é essencial para relatórios, faturamento e auditoria. Isso não é redundância, e sim informação distinta.
